### 2.3 技术深挖问题与回答

#### Q1：RAG的原理是什么？为什么要用RAG？

**回答要点**：

```
RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识检索与大语言模型生成相结合的技术。

核心流程：
1. 用户查询向量化
2. 从知识库检索相关文档
3. 将检索结果作为上下文输入LLM
4. LLM基于检索内容生成答案

使用RAG的原因：
1. 解决LLM知识时效性问题——校园政策经常更新，RAG可以动态更新知识库
2. 解决幻觉问题——LLM可能编造答案，RAG基于真实文档生成
3. 可解释性——可以标注答案来源，学校官方问答需要权威依据
4. 成本更低——比微调模型成本低，适合学生项目
```

#### Q2：检索效果不好怎么优化？

**回答要点**：

```
我建立了一套系统的优化流程：

第一步：Bad Case分析
- 收集回答不准确或检索失败的案例
- 分类定位问题：是召回不够、排序不准，还是生成有问题

第二步：针对性优化
- 召回问题：查询重写、扩展同义词、调整Embedding模型
- 排序问题：调整相似度阈值、引入重排序模型
- 生成问题：优化Prompt、添加Few-shot示例

第三步：效果验证
- 用测试集验证优化效果
- A/B测试对比不同策略

实际效果：
- 初始准确率75%，优化后达到92%
- 主要优化措施是添加查询重写和混合检索
```

#### Q3：混合检索是怎么实现的？

**回答要点**：

```
混合检索结合了向量检索和关键词检索的优势：

向量检索：
- 优点：语义理解好，能召回同义表达
- 缺点：对专有名词、ID匹配不准

关键词检索：
- 优点：精确匹配，适合专有名词
- 缺点：无法理解语义相似性

我的实现方案：
1. 并行执行两种检索，各召回Top10
2. 使用RRF（Reciprocal Rank Fusion）算法融合结果
   - 公式：score = 1/(k+rank)
   - k取60，平衡两种检索的权重
3. 使用重排序模型对融合结果精排
4. 取Top5送给LLM生成答案

效果：混合检索比单一向量检索准确率提升8%
```

#### Q4：Agent工作流是怎么设计的？

**回答要点**：

```
我设计了4类核心工作流：

1. 智能问答工作流
   - 意图识别 → 知识检索 → 答案生成
   - 如果检索结果不足，触发查询重写

2. 个性化查询工作流
   - 身份验证 → 意图解析 → 参数校验 → 调用教务API → 数据处理 → 生成回复
   - 关键：身份绑定确保数据安全

3. 事务办理向导工作流
   - 识别事务类型 → 判断用户阶段 → 提供针对性指导
   - 支持"刚开始了解""准备材料""办理中"等不同阶段

4. 多轮对话管理工作流
   - 维护对话状态（槽位填充器）
   - 支持上下文理解和指代消解

工作流调度：
- 顶层有一个意图分类器，将用户请求路由到对应工作流
- 工作流之间可以嵌套调用
```

#### Q5：项目中遇到的最大挑战是什么？怎么解决的？

**回答要点**：

```
最大挑战是知识库构建。

遇到的问题：
1. 文档格式混乱——PDF扫描件、网页、Word混用
2. 表格识别不准——很多政策以表格形式呈现，OCR识别错误率高
3. 信息冲突——不同文档对同一问题的描述不一致
4. 时效性管理——政策更新后，旧文档需要及时标记失效

解决方案：
1. 建立预处理SOP：
   - PDF转文本（OCR+人工校对）
   - 网页转Markdown（保留结构）
   - 统一编码和格式

2. 表格特殊处理：
   - 开发表格转文本脚本
   - 关键表格人工录入

3. 冲突检测机制：
   - 添加文档时间戳
   - 标记优先级（以最新文档为准）
   - 答案中标注来源，让用户判断

4. 版本管理：
   - 建立文档审核流程
   - 定期清理过期文档

效果：
- 知识库准确率从70%提升到95%
- 建立了可复用的知识库构建方法论
```

### 4.2 可能的答辩问题

1. **为什么选择Coze平台而不是自己开发？**
   - 答：Coze提供完整的RAG和Agent能力，适合快速验证；作为本科项目，重点在应用创新而非底层开发。

2. **RAG和微调的优缺点对比？**
   - 答：RAG更适合知识频繁更新的场景，成本低；微调适合风格定制，但成本高、更新慢。
